## 结果

### 一、修复补抓分类缺陷（运行前）

- 现象：`crawl plan` 把 4 项未关闭的 fetch 失败分成 `refetch` 2 项 + `manual` 2 项
  （“永久 4xx，只记录不重试”）。
- 原因：`http_status_of` 的消息正则 `\b(?:HTTP\s*)?(\d{3})\b` 会把超时消息里的端口号
  `port=443` 当作 HTTP 443/4xx，瞬时读取失败被误判为永久 4xx。
- 修复：改为只识别显式 HTTP 前缀 `\bHTTP\s+(\d{3})\b`；失败账新增结构化
  `http_status` 字段（`FailureWriter.record` + 6 个 `_record_failure` 调用点），
  分类优先用结构化状态码，不再依赖错误文案。
- 回归测试（`tests/test_recovery.py`）：端口号不再计为状态码、结构化状态码优先、
  消息中的其它数字忽略；`tests/test_recovery.py` 21 项、`tests/test_attachment_coverage.py`
  6 项通过。
- 修复后 `crawl plan`：4 项全部为 `refetch`（IN-02 三条附件 + IN-05 大 PDF）。

### 三、本轮发现的边界一致性问题与修复（补抓路径大小上限）

- 现象：`JP11B0043.pdf`（69 MiB）与 IN-05 年报 PDF（155 MiB）均**超过 64 MiB 声明上限**，
  附件下载路径会按 `AttachmentBoundaryRejected` 边界拒绝，但 `resume` 的补抓路径
  （`_recover_refetch` → `_collect_target` → `http.get`）没有同样的上限，原件被直接归档。
- 影响：同一 URL 在采集路径（下载器、待处理续传）被边界拒绝，在补抓路径被放行，
  已声明边界在入口之间口径不一致；`JP11B0043.pdf` 的旧失败记录本身就来自上限拒绝
  （修复前的历史行），补抓把它当作普通网络失败重取。
- 修复：目标获取路径改为 `_fetch_target_response`——非 HTML 原件按块读取并执行
  `Downloader.max_bytes` 的同一上限（与 `Downloader.download` 共用新增的
  `iter_capped_chunks`），超限抛 `AttachmentBoundaryRejected`，`_collect_target` 按
  `boundary_rejected:size_limit_exceeded:<bytes>` 记跳过（不写失败账、不进重试、
  计入覆盖口径）；`_recover_refetch` 对边界拒绝按 `skip` 关闭失败记录。HTML 页面不受附件上限约束。
- 回归测试：`test_resume_refetch_enforces_attachment_size_cap`（补抓超限附件 → skip 关闭、
  不写失败账、不产出原件）、`test_resume_refetch_html_page_ignores_attachment_size_cap`、
  `test_direct_non_html_target_enforces_size_cap`（直达非 HTML 目标同口径）。
  全量测试 **450 passed**（修复前 447 + 新增 3 项）。
- 已归档的两份超限原件按 raw 优先保留，不删除、不覆盖；作为修复前补抓路径的历史例外记录在案，
  修复后同一计划复查为 0 项，不再重取。
