## R6：读取失败必须使对账失败（已实现，`f53a899`）

定位：validate/reconcile.py 当前丢弃 _pending_items 和 load_jsonl_rows 的错误列表。

方案：将文件读取/JSON 解析/结构错误写入 ReconcileReport.problems，ok=false，CLI check 返回非零。区分允许缺失的初始状态文件与已经存在但损坏的文件；校验 items 为映射、条目为对象及必要身份/状态合法，禁止把非法类型或空值静默转换成正常空队列。只读检查不得覆盖或重建损坏文件。

验收：截断 JSON、合法 JSON 但 items 类型错误、非法条目、损坏失败账均报错；合法空状态按约定处理；检查前后原文件字节不变。给出文件与原因，不能因抛未捕获异常失去可读诊断。

## R5：恢复以明确结果判定，不用计数替代状态（已实现，`f53a899`）

定位：pipeline._recover_fetch 以 resources/documents 非零判断恢复成功，即使 _collect_target 已返回失败。

方案：以 TargetOutcome 与恢复任务所属阶段为依据。取得 raw、解析成功、规范化成功、正文仍不完整分别记录；原 fetch 阶段若确已解决可以关闭它，但派生 parse/normalize 失败必须保持开放，不能把整个目标标 processed。明确失败保持 failed；预算停止保持待续；合法访问拒绝记 skipped。只有完整结果或具备完整既有实体的合法 304 才能关闭目标。

恢复关联必须匹配 source、原 scope、任务类型和必要的 doc_id/母页关系，不能以相同 URL 批量关闭其他窗口或附件关系。reconcile 同步采用该身份口径，不能只按 URL 最后一行推断所有任务已恢复。保留追加式历史；若需关联字段，用可兼容扩展并登记迁移。

验收：HTTP 200 且 raw 留存后解析失败、规范化失败、partial、304、robots 拒绝各有不同结果；同 URL 不同 scope/母文档不会互相关闭。失败重试成功后，队列和对应失败链一致，不能通过新增 recovered 行掩盖尚未解决的问题。

## R3：归档 ID 与原件写入使用同一跨进程临界区（已实现，`8bbbdda`）

定位：output/archive.py 的 next_crawl_id 使用各实例 _sequences 缓存；现有状态文件锁不覆盖编号及账本追加。

优先方案：复用 file_lock，为同一数据根设统一归档锁。锁内重新读取已落盘编号、写原件并校验、分配 ID、追加并刷盘账本；所有归档入口必须经过同一服务。不要仅锁 next_crawl_id 后解锁再写账，不能继续依赖实例旧缓存。归档锁外再处理 pending/cursor，规定锁顺序，避免嵌套同路径死锁。原件同名写入也在保护范围，不能只修 ID 而保留覆盖竞争。

若直接公开编号分配接口，须将其收敛为归档事务内部方法，或实现持久化预留，不能返回未被持久化保留的编号。崩溃后遗留无引用原件可诊断复用，不能出现账本引用不存在/错误字节。

验收：目标 Linux 中两个真实进程同来源同日写不同内容、同名原件及相同字节；ID 唯一、JSONL 可读、每行哈希与原件一致。再验证两个长寿命实例交错归档，排除缓存编号回退。单纯多线程各写不同 cursor 的旧用例不足以关闭本项。未支持跨进程锁的平台明确限制，不声称等价安全。

## R4：先持久化目标，再推进发现游标（已实现，`ec2edd3`）

定位：Discoverer 在返回目标前 _update_cursor，pipeline 稍后 enqueue_targets。

方案：按页提交已归档响应对应的目标，再持久化下一页游标。队列写入失败不推进游标；队列成功但游标写入失败时允许重放本页，以稳定身份去重。区分“页重放幂等入队”与“新复查轮次刷新旧目标”，不能重放时把全部 processed 转成 refresh。

优先采用已有 JSON 状态与锁，加小型提交回调/共享协调方法，不引入新消息队列。主目标身份包含来源、scope、URL；游标包含入口与发现方式。并发同入口要防旧提交覆盖较新进度，可使用入口级运行锁或版本检查。一个策略结束前发生异常不能丢弃之前页的已发现目标。

验收：故障注入在入队前、入队后游标前、游标落盘后；重启继续后发现目标集合不丢，既有原件可回指。至少覆盖列表与发现 API；模拟后一个发现策略失败，前一个策略目标仍留存。中断重放不造成无限 refresh。

## R2：正文分页独立保存待续状态（已实现，`9f74bd1`）

定位：_expand_body 遇预算停止仅返回 partial；_collect_target 记录成功状态并将主目标 processed。

方案：持久化母目标/文档身份、scope、已取得部分的 crawl_id/raw 引用、下一正文 URL 或 API、部分顺序与停止原因。预算停止是正常待续，不写成请求失败，也不能写成整个目标完成。主目标继续状态和正文部分任务可按现有 pending 扩展，优先复用当前状态机制。

继续执行优先消费未完成正文，直接请求未取部分；若母页需要校验，304 仅说明母响应未变，不能取消其未完成正文/附件。防重复页、循环、日期窗口混淆，最终规范化不得重复拼接已保存块。原文档快照及已取得 raw 保留；最终文档与旧 partial 的版本/关系沿用并明确现有契约，不静默覆盖历史。

验收：三页正文在第二页前耗尽预算，重启时母页返回 304，仍能完成第二/三页、正文 API 和适用附件；全部 raw 可回指，块顺序正确且无重复，待续状态最终关闭。正文请求失败进入对应失败链，合法边界拒绝保持可解释的不完整状态。

## R1：URL 已知不等于内容未变或窗口没有新增（已实现，`b925705`）

定位：discoverer._walk_html_pages 在首个全为 known_target 的页面提前 break，且该页目标尚未加入 refresh。

默认方案：取消通用的“全为已知 URL 即 complete=true”推断。已知目标按现有增量更新策略进入必要复查，使用条件请求；发现新 URL 和更新既有 URL 是两条独立状态。复查需有到期/轮次和预算边界，不能每次发现都无限重排全部历史目标。

没有站点级顺序保证时，分页按保存游标有限推进，覆盖未复查区间；站点插入/置顶/补录不能因第一页 URL 不变而丢失。确有证据可使用头部快速检查时，只报告“头部检查范围内未发现新链接”，不代表完整窗口；另有可推进的覆盖周期，不能无限停在第一页。快检优化为可选策略，不默认扩成守护进程或按小时调度。

历史 completed/pages_fetched 需区分一次遍历覆盖与反复请求累计数，不以累计次数充当覆盖页数；旧 incremental_head_checked 标记为待重新核实，不破坏原日志。迁移已有游标时记录旧状态来源，不能由旧标记自动断言新语义下已完成。

验收：第一页均已知但第二页新增、相同 URL 正文变化、置顶及无序结果、新目标出现在后部、无变化来源跨预算推进。每项报告本轮范围和停止原因；队列无 pending 不足以使 discovery_complete 为真。
