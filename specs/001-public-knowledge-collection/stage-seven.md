## 范围与完成口径

- 保留 18 来源配置、运行时起始时间、按站发现、raw/manifest、标准化、最小结构分块、增量和恢复能力。Python/uv、镜像与现有依赖组合不重选。
- 基础成品允许存在已登记的运行异常和非阻断局限，能够由有限重试、离线重解析、来源暂停或人工处置管理。不新增错误管理平台、数据库、Web 界面或值守服务；优先复用现有失败账、队列、CLI 与运行报告。
- “软件成品可交付”与“某来源某窗口数据采集完整”分别判定。18 来源都必须有能力和限制说明；受限来源不因尚未恢复访问而阻断软件交付，但必须标明受限/未验证，不能计为采集通过。不能以错误账代替尚未实现的常规核心功能。
- 成功获取的业务响应应留存原件和 manifest，已输出 documents/blocks 必须 100% 可追溯；这些不变量保留。遇磁盘/写入失败应明确失败并停止受影响写入，不能承诺不可实现的“任何硬件故障都不丢内存响应”。
- 不承诺全网召回 100%，不要求队列和错误账清零。不将未抓到、被拒绝或待补抓对象从数据报告中消失。原文质量要求和历史 AT 状态保留，当前软件成品验收不冒充全部业务数据验收。
- 高级 OCR/语义质量、RAG、检索、发布平台及最终部署仍不在范围内；交付使用 Git 版本与已有运行说明。

## S7-02：建立可操作的错误账闭环（待核对与补齐）

现有 `manifests/failed_records.jsonl` 是运行错误事实来源，pending/cursor 是执行状态，运行日志提供上下文；不建立另一份与它们竞争的运行错误真值。工程缺陷及接受的局限汇总到阶段交付报告，通过身份与证据链接关联运行记录。

先盘点已有 `plan/resume/check` 和失败账能力。已有功能直接复用；仅补齐不能完成下述操作的缺口。若命令不支持某动作，增加最小接口并写真实用法，不能只在文档中宣称可操作。

### 分流规则

| 类别 | 处理 | 是否阻断基础成品 |
| --- | --- | --- |
| 静默丢 raw、伪造完整/成功、跨对象误关闭、不可追溯输出、损坏状态误报通过 | 修复或可靠隔离；明确失败、保护历史数据，并留定向证据 | 未控制前阻断；单纯登记或转人工不足以放行 |
| 超时、429、临时 5xx、网络波动 | 按已有限速与有限重试预算；耗尽后保持待补抓并退出本轮，遵守 Retry-After | 处置路径有效且不破坏主流程时不阻断 |
| robots 拒绝、验证码、登录、访问限制、长期下线 | 停止受影响请求，登记限制和重新检查触发条件；不绕过，不轮询等待 | 不阻断软件；该来源/数据对象保持受限或未完成 |
| 个别坏文件、不支持版式、解析失败、正文 partial | 保存 raw，标明失败/partial；可离线重解析或人工处置；不让一个对象阻塞其他对象 | 有记录且能隔离时不阻断；普遍失效导致常规核心流程不可用须修复 |
| 性能优化、复杂版式精度和范围外能力 | 记录影响和后续触发条件，进入后续维护 | 不阻断，不为其追加本阶段测试循环 |

### 最小记录与处置要求

1. 错误可按来源、原运行时间范围、URL、阶段、对象类型及必要 doc_id/母页关系定位；包含错误类型/原因、发生时间、尝试次数、下一动作及已有原件/账本引用。字段按现有契约复用；确需扩展时先同步 data-model/structure-comparison 与受影响 schema，兼容读取旧记录，不批量改写历史。
2. 区分待补抓、恢复成功、合法跳过和人工处理。复用现有 `retry_later/record_only/recovered/skip/manual_review` 语义；manual_review 仍要在报告中可见，不能等同 recovered。预算停止使用待处理状态，不伪装网络错误。
3. 自动重试有明确次数/请求/时间预算，沿用已有参数并在证据中写实际值；耗尽后结束本轮。禁止无限 retry 或定时重跑相同失败。人工处理写明可执行动作、由运行维护人员处理、何种条件下重试/重解析/保持限制，以及已接受的影响。
4. 处置通过追加记录保留历史，且只更新匹配的执行对象；操作可重复执行而不误关闭其他来源/范围。失败的失败账写入本身必须可见并停止受影响流程，不能吞异常继续报告成功。
5. 提供一次有界错误摘要：开放失败、人工处理、受限、待处理及 partial 的数量和样例身份，注明聚合口径，区分事件数与对象数。可按需生成报告，无需常驻监控。重试成功、预算耗尽、人工/限制保留三条路径各用已有证据或一个最小例子证明可操作。
